# The JSON Archive

LOOP stores every catalog record twice: as plain JSON files on disk, and as
documents in MongoDB. The files are authoritative. MongoDB is an index over
them — queryable, transactional, fast, and entirely rebuildable.

This document explains why, how it works, and what to do when something breaks.

## Why

Before this, LOOP's only durable record was MongoDB, and its only backup was
`mongodump --gzip --archive` — an opaque binary tied to a compatible `mongod`.
That is a reasonable operational backup and a poor archival one. A research
catalog of high-entropy materials records experiments that took months of
furnace time; those records should outlive the database engine, this codebase,
and the version of Python it runs on.

The archive is designed so that someone with nothing but the directory can
recover the science: sorted, indented UTF-8 JSON, one file per record, in a
directory tree named after the AUIDs it describes, next to the original
uploaded files.

## Guarantees

**Archive-first.** Every write lands on disk *before* it reaches MongoDB. The
hook runs on MongoEngine's `pre_save_post_validation` signal, which fires after
validation and before the driver is handed the document — so if the disk write
fails, the database write never happens. The two cannot disagree in the
direction that loses data.

Set `ARCHIVE_REQUIRED=0` to downgrade this to log-and-continue during a disk
incident. Failures are recorded in `ARCHIVE_ROOT/.state/drift.json` and
reported by `loop_archive verify`.

**Complete coverage without call-site discipline.** The hooks attach to the
document layer, so all ~100 `.save()` and `.delete()` call sites across
`views.py`, `api/`, `services/`, and the workers are covered at once, including
code not yet written. The five paths that write to Mongo without a document —
`raw_db.record_raw_file`, `documents.upsert_user_affiliations`, the superuser
JSON editor, `xrd_store.store_raw_file`, and the AFLOW bulk import — call the
writer explicitly. `loop_archive verify` catches any that regress.

**Deletion is real.** Removing a trial through the UI removes it from the
archive and journals a tombstone carrying its final body. Note that this makes
the archive a faithful record of *the catalog*, not an immutable ledger of
everything ever typed: if a user deletes a record, it leaves `records/`. The
journal retains the tombstone and the deleted body.

## Layout

```
ARCHIVE_ROOT/
  ARCHIVE.md                  format description, regenerated by `export`
  schema_version.json
  records/                    current state, one file per record
    materials/M-<hash>/material.json
    materials/M-<hash>/recipes/R-<short>/recipe.json
    materials/M-<hash>/recipes/R-<short>/trials/<trial_id>/trial.json
    materials/M-<hash>/recipes/R-<short>/literature/<lit_id>.json
    raw-files/<ab>/<cd>/<sha256>.json
    users/<username>/{affiliations.json,precursors/,protocols/}
    xrd-analyses/<analysis_id>/{job.json,reviews/}
    synthesis-predictions/, synthesis-cache/, models/
  blobs/sha256/<ab>/<cd>/<sha256><ext>     original uploads, content-addressed
  journal/<YYYY>/<MM>/<YYYY-MM-DD>.jsonl   append-only event log
  .state/drift.json                        recorded write failures, if any
```

Colons in AUIDs become hyphens in path segments (some filesystems reject them),
matching the `api_download` zip layout.

Trials and literature live in their own files rather than inline in
`recipe.json`, which keeps any one file small and mirrors the download format.
`recipe.json` carries `trial_ids` / `literature_ids` as an index. Embedded DFT
calculations *do* stay inline in `material.json` — they are small and have no
independent identity in the UI.

## The journal

Every create, update, and delete appends one line to a per-UTC-day JSONL file,
with the full body inlined:

```json
{"ts": "...", "op": "upsert", "kind": "trial", "key": "M:abc:R:7f8e/1",
 "path": "records/...", "sha256": "...", "prev_sha256": "...",
 "actor": "pboctor", "source": "web", "body": {...}}
```

Inlining bodies costs storage and buys independence: losing `records/` and
losing `journal/` are separate failures, and either alone can rebuild the
catalog. `loop_archive replay` proves it by reconstructing from the journal
with `records/` deleted.

Writes that change nothing are skipped — no file write, no journal entry. This
matters because `_upsert_material` re-saves an unchanged `Material` on every
trial upload; without the skip, the journal would be mostly noise.

## Commands

```bash
# Summary: counts, journal extent, drift.
python manage.py loop_archive status

# MongoDB -> archive. Bootstraps an archive from an existing database,
# and repairs drift. Idempotent.
python manage.py loop_archive export

# Compare without changing either. Exits non-zero on divergence.
python manage.py loop_archive verify

# archive -> MongoDB. Drops and repopulates.
python manage.py loop_archive rebuild --yes --target-db loop

# journal -> MongoDB. Same result, reconstructed from events alone.
python manage.py loop_archive replay --yes --target-db loop
```

`--target-db` must name the database the connection actually points at. It is
an explicit confirmation, not a connection setting: `rebuild` drops
collections, and a command that defaults to whatever `MONGODB_URI` happens to
name is one mistyped prompt away from wiping production.

## Why export streams, and why the workers must be off

`export` reads one document and writes it before moving to the next, and
`loop_archive` is listed in `catalog/apps.py::_NON_WEB_COMMANDS`. Both exist
for the same reason, learned the hard way on a 35,695-material catalog.

An earlier version buffered an entire collection before writing any of it,
while the ChemScreen retraining and XRD analysis worker threads ran alongside
it (because the command was not in `_NON_WEB_COMMANDS`). Those workers write to
MongoDB. So a material read at the start of the pass could be modified before
its already-stale payload reached disk, and `verify` then reported ~1,500
records as diverged — correctly. The archive really did disagree with the
database.

Streaming shrinks that window to a single document. Keeping the workers out of
archive commands closes it. The same reasoning applies with more force to
`rebuild`, where a background thread writing during a restore would corrupt it.

## Recovery drill

```bash
# 1. Confirm the archive is current.
python manage.py loop_archive verify

# 2. Rebuild into the live database.
python manage.py loop_archive rebuild --yes --target-db loop

# 3. Regenerate vector embeddings (not archived — see below).
python manage.py backfill_embeddings
python manage.py mongo_admin ensure-vector-indexes
```

Derived XRD artifacts (`pattern.csv`, overlay PNGs, peak JSON) rebuild lazily
on the first page view from the archived raw bytes; nothing to run.

## Type fidelity and the `$date` tag

Reconstruction is driven by the **declared field type**, never by sniffing a
value's shape, so a `StringField` holding `"2026-01-01T00:00:00"` stays a
string while a `DateTimeField` holding the same text becomes a datetime.

That leaves one gap. A `DictField` declares no inner types, so nothing in the
schema can restore a datetime nested inside one — `ExpCondition.additional_params`,
`EmbeddedDFT.dft_metadata`, `XRDAnalysisJob.diagnostic_metadata`, and similar
free-form containers. A bare ISO string there would silently come back as a
string after a rebuild.

Datetimes inside untyped containers are therefore written tagged:

```json
"dft_metadata": {
  "functional": "PBE",
  "measured_at": {"$date": "2026-02-14T08:05:00+00:00"},
  "looks_like_a_date": "2026-01-01T00:00:00"
}
```

`$date` is a safe sentinel because MongoEngine rejects `$`-prefixed keys in a
`DictField` ("keys may not startswith \"$\" characters"), so no legitimate data
can collide with it. Tagging is confined to untyped containers — every declared
field stays a plain readable ISO string, which is why the archive is not
MongoDB Extended JSON throughout.

`registry.decode_tagged` inverts this on rebuild and replay. Recipe children
(trials, literature) are reassembled from their own files, so they are decoded
separately from the recipe payload; `rebuild._coerce_document` covers both.

Two related notes:

- **Bytes inside a `DictField`** come back as a list of ints. MongoEngine does
  that itself in `to_mongo()`, before the archive sees the value, so it is
  pre-existing behavior and stable across a round trip — but do not store
  binary in a `DictField` and expect it back.
- **Comparing payloads cannot detect this class of bug.** Both sides run
  through the same encoder, so a real datetime and a literal `{"$date": ...}`
  dict compare equal. The tests assert on the stored BSON type directly, and
  are checked to fail when the decode is disabled.

## Django accounts

Users, groups, and API keys live in SQLite, not MongoDB, so no signal hook can
reach them. `loop_archive export` writes them to `records/auth/django-auth.json`
as a Django fixture, mode `0600`. Recovery is:

```bash
python manage.py loaddata /app/archive/records/auth/django-auth.json
```

The file contains password hashes and API-key hashes. Neither is a usable
credential — both are one-way — but they are the most sensitive bytes in the
archive, which is why the file is `0600` and why the journal records the event
without inlining the body.

Without this, a full restore returns the entire catalog and nobody can log in,
and the restored `UserAffiliation` records — which gate who may see what —
point at user IDs that no longer exist.

## What is deliberately not archived

**Derived collections.** `ml_embeddings` (regenerated by `backfill_embeddings`),
`doi_mappings` and `Material.latest_trial_date` (both regenerated by
`loop_archive rebuild` itself). Archiving 384-dimension vectors would dominate
the archive's size and guarantee drift, since they are written by paths that
bypass the document layer on purpose.

**Transient queues.** `synthesis_parse_jobs`, `model_retrain_jobs`,
`aflow_cache`. Losing these costs a re-run, not a record.

`synthesis_parse_cache` **is** archived despite looking like a cache: it maps
route text to discrete synthesis steps, and recipe AUIDs are computed from
those steps. A lost cache means the LLM re-parses and may produce different
steps, silently forking every affected recipe onto a new AUID.

## Notes for future changes

Adding a collection to LOOP means adding one `ArchiveKind` to
`catalog/archive/registry.py`. Everything downstream — hooks, export, verify,
rebuild, replay — is driven off that table.

Two details are easy to get wrong and are covered by tests:

- **Rebuild must not use `Document.save()`.** `Material.save()` and
  `Recipe.save()` stamp `updated_at = now()` unconditionally, so a save-based
  rebuild would rewrite every timestamp in the catalog. Rebuild goes through
  `to_mongo()` and raw pymongo `ReplaceOne`.
- **Datetimes are normalized to what BSON can store** (UTC, truncated to
  milliseconds) before archiving. The archive is written from the in-memory
  document but must equal what Mongo hands back; without this, every timestamped
  record would read as drifted.
- **Anything reached without a field definition must be tagged**, not written
  bare — see the `$date` section above. If you add a projection path that
  bypasses `registry._project_value`, it will silently lose types on restore.

## Deploying the `$date` change to an existing archive

An archive written before tagged datetimes stores any `DictField` datetime as a
bare ISO string. Nothing breaks — such values are already strings in MongoDB
too, so the two still agree — but run one export after deploying so the files
reflect the current encoding:

```bash
python manage.py loop_archive export
python manage.py loop_archive verify
```

`verify` will report `content_differs` for affected records until that export
runs. No data migration is needed.
